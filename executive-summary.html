Kalshi demo dashboard: what it does, what is verified, and what is not

A live market-intelligence terminal for five topics — gas prices, elections, culture, crypto and golf — built only on Kalshi’s official public demo API. It alerts on ≥ $0.10 contract swings, keeps a transparent high-ROI model feed, charts price and liquidity, follows events to their official YES/NO resolution and runs autonomous simulated trades so the strategies can be judged on results.

1. What was delivered

  • Live dashboard (dashboard.html): browser polling of the public demo API every 5 seconds, a ≥ $0.10 swing detector, two scrolling feeds (all alerts vs. model-selected high-ROI opportunities), 30-second-to-24-hour charts, an orderbook ladder with contracts at each price, and automatic paper trading.
  • Five topic pages (gas, elections, culture, crypto, golf): every tracked market in a source-linked table, recent swings, settlement sources and a resolution log.
  • Portfolio and strategy analytics (portfolio.html): per-strategy sleeves, realised equity, win rate, expectancy, drawdown, attribution by strategy/topic/price bucket, a trade log, CSV export and a separate candle backtest.
  • Python engine: REST client with Ed25519 and RSA-PSS request signing, collector, classifier, detector, scoring model, paper broker, analytics, optional FastAPI live server. Forty-seven unit and contract tests, including the official fee example and threshold edges.
  • Verification pipeline: CI collects the demo snapshot, runs a browser-CORS probe and an unauthenticated WebSocket probe, runs the tests and a link/data verifier. Raw probe output is published as data/probe.json.

4. How it works

  1. Collect. CI pages through open and recently settled demo markets, joins event/series metadata, classifies each market into one of the five topics, and enriches the selected markets with orderbooks and 1-minute/1-hour candles.
  2. Detect. Prices are the YES mid only when the book is two-sided and no wider than 25¢; otherwise the last trade is used and labelled, or the cell shows a dash. A move of ≥ $0.10 from the previous observation fires an alert. The same detector runs in Python and in the browser.
  3. Score. Each alert is evaluated by three transparent heuristics (momentum, mean reversion, favourite drift). Entry, model probability, edge, estimated ROI, spread, depth, volume and time-to-close determine a 0–100 score. Only scores ≥ 55 with estimated ROI ≥ 5% enter the high-ROI feed (the dashboard applies an additional ≥ 65 floor and a 30-second throttle).
  4. Trade (simulated). A paper broker opens a position at the ask, caps size by risk, visible depth and cash, applies the quadratic fee, exits at +$0.15/−$0.10, and settles at the official YES/NO result.
  5. Verify. Every table row links to its API record; the snapshot schema and links are checked in CI; CORS and WebSocket behaviour are measured rather than assumed; unconfirmed values are blank and flagged.

6. Key decisions

  • Static site + direct public reads. GitHub Pages cannot hold a server or an API secret. Public market data is read directly by the browser; a CI probe measures whether the exchange permits it and the page falls back to the verified snapshot with an explicit warning if it does not.
  • No order execution on the published site. Signed requests require a private key and browser preflights do not allow Kalshi’s auth headers. Execution is therefore local-only, opt-in and disabled by default.
  • Root-level publish. The repository’s Pages site is configured as a legacy build from main:/; a prior artifact deploy of docs/ reported success but the live URL served README.md. The canonical site therefore lives at the repository root, and the earlier analysis is preserved at docs/.
  • Transparent model, not a black box. Every score can be recomputed from the published inputs and formulas. No accuracy claim is made.

7. Risks, limitations and open items

  • Real demo-account trading is unverified because no demo API key was supplied. The signing code is unit-tested, but no signed request was executed against the live demo API.
  • WebSocket streaming is unavailable to a static page without exposing a key; the dashboard polls every 5 seconds instead. A local backend can add authenticated streaming.
  • CORS is measured, not guaranteed for every visitor’s network; failures are surfaced, never hidden.
  • News context is a search link, not causal evidence. The dashboard does not claim that a headline caused a move.
  • Notional and seeded moves are computed from official contracts and prices and are labelled as estimates.
  • Demo coverage is sparse and can change; empty topic tables are reported as coverage gaps.
