Executive Summary

Tradebot2 — a live Kalshi demo trading dashboard covering the five requested topics (gas prices, elections, culture, crypto, golf), built 2026-11-22 and published on GitHub Pages. Every figure on the site was verified line-by-line against official sources; irregularities are published on the Flagged for Review page; nothing was inferred.

1. What was built

  • Live dashboard — landing page + five topic subpages, each a clean table of verified markets (price, bid/ask, 24h/total notional volume, open interest, close/settle time) with per-row source links to the exact official API query, the official Kalshi website page where one was observed, and the official settlement source.
  • Live alerting system — two scrolling chats: Chat 1 logs every ≥$0.10 price swing in either direction across all tracked events; Chat 2 is the selective high-ROI model filter (transparent reversion model: K=0.6, edge ≥ $0.05, OI ≥ 1). Live mode polls the official demo API from the browser every 15s; a labeled REPLAY fallback re-runs the verified historical 1-minute BTC 15-min series so the pipeline is always demonstrable.
  • Track-to-resolution — every tracked market shows its exact verified resolution (result: yes/no, settlement_ts, settlement_value_dollars), e.g. 2026 President's Cup → Team USA (YES), BTC 15-min 26NOV201900 → NO @ $0.003, RSM Classic cut markets → NO.
  • Automated simulated trading — a deterministic paper engine (no real orders — no demo API keys exist in this session) runs four documented strategies (Momentum-Fade, Trend-Continue, Cheap-Side, Favorite-Edge) against the verified data, categorizes every trade, and computes P&L/ROI/win-rate per strategy.
  • Interactive charts — x = time with selectable seconds/minutes/hours buckets, y = contract price; verified 1-minute candlesticks for the BTC 15-min market; ≥$0.10 alert band; hover OHLCV; plus verified orderbook depth (contracts available at each price) and bid/ask liquidity.
  • Liveness/interactivity suggestions — published on the landing page (WebSocket push, price heatmap, drag-zoom, news-correlation overlay with official source links, sound/TTS alerts, one-click paper order ticket, settlement watch, parameter-set A/B, keyboard shortcuts, hourly snapshot CI).
  • Organization — topics kept separate (dedicated subpages); events within a topic grouped together in rollup tables; simplified charts and tables throughout.

4. Findings & recommendations

  • The demo environment is the right testbed but is sparse. Only a subset of Kalshi's markets exists there, several with explicit "demo strike" synthetic markers, and a few inconsistencies (F5, F6, F7, F12). Treat demo prices as plumbing tests, not market intelligence.
  • Momentum beat reversion on the verified 15-min crypto collapse (S1 lost, S2 won in the paper engine) — the reversion-based high-ROI model (K=0.6) is therefore a filter for the alert chat, not a trading signal, until it is backtested against real historical data via /historical/markets.
  • Liquidity is the binding constraint in the demo — verified books are 2–100 contracts deep; any strategy must carry an OI/size gate (the engine's ROI model does).
  • To go live-trading (still demo-safe): create demo API keys, add the signed-order client (official SDKs: Python & TypeScript), subscribe to the ticker/trade WS channels instead of 15s polling, and wire the same alert engine to the fill channel for the paper account.
  • To make the site more live: the ten suggestions on the landing page, prioritized: (1) WebSocket push, (2) price heatmap, (3) news-correlation overlay with official source links, (4) one-click paper order ticket.

5. Verification method

Each table row was retrieved from a single official query and transcribed verbatim; the exact query URL is linked on the row. Values the response did not contain are rendered as "–" and listed on the Flagged for Review page (never filled by inference). The full line-by-line log is in docs/verification.md and docs/sources.md in this repository, and on the Sources page. Site build is plain static HTML/CSS/JS (no build step), which is how GitHub Pages serves it; the integration pass checked every internal and external link before merge.
